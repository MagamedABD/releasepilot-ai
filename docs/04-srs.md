## 1. Назначение

Система управления delivery-процессом, которая рассчитывает состояние и риск
релиза, прогнозирует вероятность выпуска в срок и через AI-агента объясняет
причины риска и предлагает проверяемые сценарии его снижения.

## 2. Пользователи и роли

Пять ролей: `owner`, `admin`, `manager`, `lead`, `viewer`.
Матрица прав — ADR-003, раздел 2.

## 5. Архитектура

```
Браузер
   │
   ▼
Next.js (App Router)
   ├── Server Components — чтение данных
   ├── Route Handlers    — API, валидация Zod
   ├── Доменный слой     — движок риска, Монте-Карло, симуляция (чистые функции)
   └── Слой агента       — Claude API, tool use
   │
   ▼
Supabase: PostgreSQL + RLS + Auth + Storage
   │
   ▼
Внешние: Yandex Tracker (режим corporate) · Resend (email)
```

**Ключевое свойство:** доменный слой не зависит ни от базы, ни от модели.
Он принимает снимок данных и возвращает метрики. Отсюда — тестируемость,
детерминированность и бесплатная what-if симуляция.

## 7. Экраны

| Экран | Назначение | Роли |
|---|---|---|
| Вход | аутентификация | все |
| Кокпит релиза | состояние, риск, причины, прогноз | все |
| Задачи | список, поиск, фильтры, CRUD, зависимости | все (изменение — manager+) |
| Загрузка команд | загрузка, ёмкость, перегруз | все |
| Риски и блокеры | реестр, критическая цепочка | все |
| AI-ассистент | диалог, сценарии | все (применение — manager+) |
| Аналитика | история релизов, причины задержек, тренды | все |
| Настройки | команды, ёмкость, участники, интеграции | admin+ |

Требование курса — минимум 3 экрана. Планируется 8.

## 8. Ограничения

- Публичная инсталляция работает исключительно на синтетических данных (ADR-002).
- Реальные данные трекера обрабатываются только в режиме `corporate`.
- Система не хранит и не отображает персональные метрики производительности
  сотрудников.

Соответствуют разделу 8 устава и чек-листу ADR-003, раздел 11.
