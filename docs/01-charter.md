## 1. Название и краткое описание

**ReleasePilot AI** — AI-powered Delivery Management Platform.

Веб-приложение для управления релизами продуктовой команды, которое показывает
Delivery Manager'у реальное состояние текущего релиза и заранее предупреждает,
что релиз под угрозой: где перегрузка команд, какие блокеры критичны и какие
задачи не успеют пройти тестирование. Встроенный AI Delivery Assistant объясняет
причины риска и предлагает конкретные действия — вплоть до симуляции сценария
«если перенести эти две задачи, риск упадёт с High до Medium».

## 2. Проблема

Delivery Manager узнаёт о срыве релиза слишком поздно — обычно за 2–3 дня до даты,
когда сделать уже ничего нельзя. Информация распределена между трекером, таблицами
и головами тимлидов:

- загрузка команд нигде не посчитана — «QA перегружен» выясняется постфактум;
- цепочки блокеров не видны: одна backend-задача может держать три frontend-задачи,
  и это обнаруживается вручную;
- нет ответа на прямой вопрос «успеем ли к четвергу» в терминах вероятности;
- история прошлых релизов не анализируется, одни и те же bottleneck повторяются
  из релиза в релиз.

Существующие трекеры (Jira, Tracker, Linear) хорошо хранят задачи, но не отвечают
на вопрос **«что именно сейчас угрожает релизу и что с этим делать»**.

## 3. Цель проекта

Разработать и развернуть в продакшн работающее веб-приложение, которое:

1. агрегирует состояние релиза в одном экране (кокпит);
2. детерминированно рассчитывает готовность, загрузку команд и уровень риска;
3. прогнозирует вероятность выпуска к заданной дате;
4. через AI-агента объясняет причины риска и предлагает проверяемые сценарии
   снижения риска;
5. накапливает историю релизов и показывает динамику качества delivery.

**Учебная цель:** продемонстрировать полный цикл разработки с применением
AI-агентов на каждом этапе — от генерации идеи до деплоя и аудита безопасности.

## 4. Целевые пользователи

| Роль | Задача | Главная ценность |
|---|---|---|
| Delivery Manager | ведёт релиз, тушит пожары | раннее предупреждение + что делать |
| Руководитель / CPO | принимает решение о переносе | короткий статус и вероятность даты |
| Тимлид (FE/BE/QA) | планирует загрузку команды | видит перегрузку и блокеры своей команды |

## 5. Границы проекта (scope)

### Входит в MVP

- Релизы, задачи, статусы, приоритеты, оценки трудозатрат, ответственные
- Команды и ёмкость (capacity) на период
- Зависимости между задачами и блокеры
- Детерминированный движок расчёта риска и готовности
- Вероятностный прогноз даты релиза (Монте-Карло)
- AI Delivery Assistant с инструментами (tool use), включая what-if симуляцию
- Аналитика прошлых релизов
- Email-дайджест «статус релиза для руководства»
- Импорт данных из внешнего трекера (коннектор Yandex Tracker) с анонимизацией
- Аутентификация, OAuth2, роли, поиск и фильтрация, загрузка файлов

### Не входит (осознанно вынесено за границы)

- Полноценная мультипроектность с раздельными правами на проект
- Кастомизируемые workflow статусов под каждую команду
- Двусторонняя синхронизация с трекером (только импорт)
- Мобильное приложение (только адаптивная вёрстка)
- Биллинг и тарифы

## 6. Ключевые архитектурные решения

Зафиксированы до начала разработки, детали — в `docs/adr/`.

| № | Решение | Обоснование |
|---|---|---|
| 1 | Риск считает код, LLM объясняет | детерминированность, тестируемость, воспроизводимость демо |
| 2 | Прогноз даты — Монте-Карло с откатом на простой расчёт | вероятность убедительнее бинарного «успеем/не успеем» |
| 3 | Движок расчёта — чистая функция от снимка данных | это единственный способ получить what-if бесплатно |
| 4 | Публичный деплой работает только на синтетических данных | реальные данные трекера не попадают в интернет |

## 7. Технологический стек

| Слой | Технология | Почему |
|---|---|---|
| Frontend | Next.js 16 (App Router), TypeScript, Tailwind, shadcn/ui | рекомендован ТЗ курса, SSR + API в одном приложении |
| Backend | Next.js Route Handlers + Supabase | быстрый старт, не пишем auth руками |
| БД | PostgreSQL (Supabase) | требование ТЗ курса |
| Auth | Supabase Auth + OAuth2 (Google/GitHub) | закрывает обязательное требование и доп. функцию |
| AI | Claude API, tool use, prompt caching | агент с инструментами, а не чат-обёртка |
| Хранилище | Supabase Storage | импорт файлов, вложения |
| Деплой | Vercel | preview-окружение на каждый PR |
| CI/CD | GitHub Actions | lint → typecheck → test → build → deploy |
| Тесты | Vitest (unit), Playwright (e2e) | движок риска обязан быть покрыт тестами |

## 8. Критерии успеха

Проект считается выполненным, когда одновременно верно:

- [ ] Приложение доступно по публичному URL и работает стабильно
- [ ] Реализованы ≥3 экрана, адаптивные на десктопе и мобильном
- [ ] В БД ≥3 связанные таблицы (план — 10+), работает CRUD
- [ ] Работает аутентификация и валидация данных
- [ ] Реализованы ≥2 дополнительные функции (план — 5)
- [ ] Настроен автоматический деплой через CI/CD
- [ ] Движок расчёта риска покрыт юнит-тестами, тесты зелёные
- [ ] AI-агент отвечает на вопросы и выполняет what-if симуляцию
- [ ] README содержит описание, инструкции запуска, стек, скриншоты
- [ ] `AI_JOURNAL.md` документирует применение AI на всех этапах с промптами
- [ ] Подготовлена презентация и выжимка для защиты

## 10. Риски проекта

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Раздувание scope (11 сущностей) | высокая | высокое | MVP-ядро зафиксировано в п.5, остальное — в бэклог |
| LLM врёт в цифрах на демо | средняя | критическое | ADR-1: все числа считает код, модель их не трогает |
| Демо-данные не показывают риск | средняя | высокое | срежиссированный сид-генератор + кнопка сброса демо |
| Утечка корпоративных данных в публичный деплой | низкая | критическое | анонимизация на импорте, секреты только в env, аудит перед деплоем |
| Не хватит времени на тесты и документацию | средняя | высокое | журнал AI и тесты ведутся с первого коммита, а не в конце |
| Превышение лимитов/стоимости AI API | низкая | среднее | prompt caching, дешёвая модель для простых операций, лимит запросов |

## 11. Ограничения

- Реальные данные Yandex Tracker используются **только локально** и только для
  калибровки модели; в публичную базу попадают исключительно синтетические данные.
- Секреты (токены, ключи API) хранятся в переменных окружения и никогда не
  коммитятся; `.env` в `.gitignore` с первого коммита.
- Названия реальных компаний, провайдеров и сотрудников в проекте не используются.
