# Концепция интерфейса

**Дата:** 2026-09-20
**Связанные документы:** [ТЗ](04-srs.md) · [User Stories](03-user-stories.md) ·
[ADR-001 движок риска](adr/ADR-001-risk-engine.md)

---

## Принцип

Delivery Manager открывает систему не изучать, а получить ответ. Значит первый
экран обязан ответить на вопрос «всё ли в порядке» без единого клика, а все
остальные — показывать причину того, что он увидел на первом.

Отсюда три правила:

1. **Вывод раньше данных.** Сначала уровень риска и готовность, потом цифры,
   из которых они получены.
2. **Каждое число — ссылка.** «Заблокировано: 4» ведёт к списку этих четырёх
   задач, а не просто информирует. Число, из которого нельзя провалиться
   в подробности, бесполезно.
3. **Никаких цветов без подписи.** Красный означает «риск High», и это написано
   словами. Дальтонизм и печать в ч/б не должны ломать смысл (NFR-17).

## Карта экранов

```
Вход
 └── Список релизов ◄── стартовая страница после входа
      ├── Кокпит релиза (риск, причины, загрузка команд, блокеры, цепочка)
      │    ├── Сценарии (подбор, what-if, применение)
      │    └── AI-ассистент (диалог, предложения сценариев)
      ├── Задачи (список, фильтры в адресе)
      └── Аналитика (история поставки)
```

Требование курса — минимум 3 экрана. Реализовано 6 (плюс вход, регистрация
и онбординг).

**Что изменилось против первой версии карты.** «Загрузка команд» и «Риски и
блокеры» задумывались отдельными экранами, а стали блоками кокпита. Причина
не в экономии: вопрос «кто перегружен» и вопрос «почему риск высокий» —
один и тот же вопрос, заданный с двух сторон, и разводить их по страницам
значит заставлять менеджера держать в голове числа с предыдущего экрана.
Разделы ниже сохранены как описание этих блоков, а не отдельных страниц.

Экран настроек (команды, ёмкость, участники, импорт) не реализован: ёмкость
правится через `PUT /api/teams/:id/capacity`, импорт — через
`POST /api/import/file`, и форма к ним — работа, не добавляющая к проекту
ни одного решения, которое стоило бы показать. Это сознательный пропуск, а
не забытый пункт.

**Список релизов** — стартовая страница после входа, и описывать её
отдельным разделом нечего, кроме одного решения: сортировка. Она не по
дате, а по срочности — идущие релизы сверху, внутри группы по скору риска.
Менеджер открывает список, чтобы узнать, где горит, а не чтобы посмотреть
календарь. По уровню риска сортировать нельзя: два релиза могут оба
оказаться «высокими» при скорах 39 и 8, и список поставил бы их рядом как
равные.

## Экран 1. Кокпит релиза

Главный экран. Структура сверху вниз повторяет логику вопроса менеджера.

```
┌─────────────────────────────────────────────────────────────┐
│ Release 2026.09.24            План: 24 сентября (через 4 дня)│
├─────────────────────────────────────────────────────────────┤
│  РИСК: HIGH          Готовность 78%       Выпуск в срок: 38% │
│  ▲ повысился вчера   по трудозатратам     Монте-Карло, 5000  │
├─────────────────────────────────────────────────────────────┤
│  Всего 64 · Готово 41 · В работе 12 · Тестирование 7 · Блок 4│
├─────────────────────────────────────────────────────────────┤
│  Почему High                                                 │
│   1. QA загружен на 135%            вклад 24  → к загрузке   │
│   2. Две задачи P0 заблокированы    вклад 18  → к блокерам   │
│   3. PPT-311 блокирует 3 задачи FE  вклад 14  → к цепочке    │
│   4. 7 задач не пройдут тестирование вклад 10 → к задачам    │
├─────────────────────────────────────────────────────────────┤
│  [ Спросить ассистента ]   [ Смоделировать сценарий ]        │
└─────────────────────────────────────────────────────────────┘
```

**Что важно в этой раскладке.** Уровень риска и готовность стоят рядом, потому
что поодиночке они лгут: 78% готовности выглядят хорошо, пока не видно, что
риск High. Причины отсортированы по вкладу — тому самому `contribution`
из `RiskReason` (ADR-001), а не по порядку написания кода. Каждая строка
причины кликабельна и ведёт на экран с соответствующими задачами.

Подпись «по трудозатратам» обязательна (FR-17): 78% по часам и 78% по числу
задач — разные числа, и подмена одного другим — классический способ обмануть
себя.

## Экран 2. Задачи

Таблица с фильтрами. Фильтры отражаются в URL (FR-09), чтобы состояние можно
было переслать в переписке: `/tasks?release=…&status=blocked&team=qa`.

| Колонка | Замечание |
|---|---|
| Ключ | `PPT-311`, ссылка на карточку |
| Заголовок | поиск по подстроке, индекс GIN (NFR-02) |
| Статус | цветной бейдж **с текстом** |
| Приоритет | P0–P3 |
| Команда | |
| Оценка, ч | |
| Блокировка | «3 дня» вместо галочки — длительность важнее факта |

Карточка задачи открывается панелью сбоку, не отдельной страницей: менеджер
смотрит задачу в контексте списка, а не вместо него. В карточке — зависимости
в обе стороны («блокирует» / «заблокирована»), и попытка создать цикл даёт
объяснение причины, а не общую ошибку (FR-13).

## Блок кокпита: загрузка команд

Горизонтальные полосы по командам. Отметка 100% — сплошная линия; всё правее
неё подписано как перегрузка с указанием, сколько часов лишние.

```
Frontend  ████████████░░░░░░  72%    58 ч из 80 ч
Backend   ████████████████░░  94%    75 ч из 80 ч
QA        ██████████████████▌ 135%   54 ч из 40 ч   перегруз 14 ч
```

Ёмкость — знаменатель — берётся из `team_capacity` за вычетом отсутствий.
Рядом ссылка «изменить ёмкость» для роли lead и выше: менеджер, увидевший
перегруз, чаще всего тут же хочет проверить, верна ли ёмкость.

---

## Блок кокпита: риски и блокеры

Две части на одной странице.

**Реестр блокеров** — таблица, отсортированная по длительности блокировки
по убыванию. Застарелые (дольше `staleBlockerDays`) помечены отдельно:
блокер на три дня и блокер на три часа — разные события.

**Критическая цепочка** — последовательность задач с суммарной длительностью
и сравнением с остатком дней до плановой даты. Если цепочка длиннее остатка,
это сказано словами: «цепочка 6 дней при 4 оставшихся — релиз не успевает
по зависимостям».

## Экран 3. Сценарии

Три блока сверху вниз — в порядке разговора, а не данных.

**Что предлагает система.** Подбор считается сразу, без нажатий: пришедший
сюда уже видел в кокпите высокий риск и хочет ответ, а не пустую форму.
Цель — на один уровень ниже текущего, а не «low»: предложение «перенесите
девять задач» верно арифметически и бесполезно практически.

Отдельно обработан случай, когда переносом цель недостижима. Его не
выдумывали: на каноническом сценарии уровень `high` держит правило
эскалации — заблокированная задача P0, — и перенос обычной работы его не
снимает. Экран тогда говорит прямо: «заблокирована задача P0, её надо
разблокировать, а не переносить», и показывает лучшее, что нашлось.

**Своя гипотеза.** Отметить задачи, добавить часов командам, посчитать.
Расчёт и сохранение — одна форма с двумя кнопками: две формы потребовали бы
держать отмеченное в двух местах, а расхождение означало бы, что сохранён
не тот сценарий, который посчитали.

**Сохранённые сценарии.** У каждого — эффект, посчитанный при сохранении, а
не пересчитанный сейчас: сценарий обещал именно это, и подменять обещание
свежим расчётом значило бы незаметно менять то, на что человек согласился.
Применяет человек кнопкой; агент применить не может (ADR-003, §6).

```
┌── Что предлагает система ───────────────────────────────┐
│ Чтобы уровень опустился до Medium, убрать 2 задачи:     │
│  PPT-330  Прогон регресса        P2 · 14 ч  скор → 61.2 │
│  PPT-331  Отчёт по возвратам     P2 · 14 ч  скор → 52.8 │
│                                                          │
│ Скор риска    84.2 → 52.8     −31.4                      │
│ Уровень       High → Medium                              │
│ В срок        0%   → 34%      +34                        │
└──────────────────────────────────────────────────────────┘
```

## Экран 4. AI-ассистент

Диалог. Ответ стримится (FR-24), первый токен ≤ 3 с (NFR-05).

Два элемента отличают его от обычного чата:

**Вызовы инструментов видимы.** Пока модель работает, пользователь видит
строки вида «смотрю загрузку команд», «считаю сценарий». Это не украшение:
менеджер должен понимать, на основании чего получен ответ, иначе рекомендации
нечем доверять.

**Предложение сценария — отдельный блок, а не текст.** Когда агент вызывает
`propose_scenario`, в диалоге появляется карточка с метриками «до» и «после»
и кнопкой «Применить». Кнопка доступна manager+ и вызывает
`POST /api/scenarios/:id/apply`. Агент нажать её не может (ADR-003, §6).

```
┌── Предложение ──────────────────────────────────┐
│ Перенести 3 задачи в следующий релиз            │
│                                                  │
│ Риск        High  →  Medium                      │
│ В срок      38%   →  71%                         │
│ QA          135%  →  98%                         │
│                                                  │
│ PPT-402, PPT-418, PPT-455    [Показать] [Применить]│
└──────────────────────────────────────────────────┘
```

## Экран 5. Аналитика

История релизов: доля выпущенных в срок, средняя задержка, ранжирование
повторяющихся причин. Строится по `release_snapshots`, поэтому показывает,
как система оценивала релиз тогда, а не как оценила бы сейчас.

---

## Три состояния каждого экрана

Требование NFR-06. Ни один экран не считается готовым, пока не реализованы все
три.

| Состояние | Как выглядит |
|---|---|
| Загрузка | скелетон той же формы, что и контент — без скачка вёрстки |
| Ошибка | что произошло, что делать, кнопка «Повторить». Без стектрейсов (NFR-08) |
| Пусто | почему пусто и что сделать: «В релизе нет задач. Добавить» |

Отдельно: **отказ AI-сервиса**. Панель ассистента показывает «Ассистент
временно недоступен», остальные экраны работают полностью (NFR-07). Это
проверяется тестом, а не наблюдением.

## Адаптивность

| Ширина | Поведение |
|---|---|
| ≥ 1280 px | полная раскладка, таблицы целиком |
| 768–1279 px | боковое меню сворачивается в иконки |
| 360–767 px | таблицы превращаются в карточки; кокпит и ассистент остаются полноценными — это то, что смотрят с телефона перед встречей |

## Доступность

- Навигация с клавиатуры по всем интерактивным элементам, видимый фокус.
- Контраст по WCAG AA.
- Статус и риск передаются текстом, цвет — дублирующий канал.
- Диалог ассистента объявляет появление ответа для скринридера.

## Что сознательно не делается

| Не делаем | Почему |
|---|---|
| Диаграмма Ганта | требует точных дат начала задач, которых в трекере нет; красивая ложь |
| Графы зависимостей «паутиной» | на 300 задачах нечитаемы; критическая цепочка списком полезнее |
| Дашборд по сотрудникам | прямой запрет из [анализа конкурентов](02-competitors.md) — система не измеряет людей |
| Настраиваемые виджеты | раскладка отражает логику принятия решения; свобода тут вредит |
