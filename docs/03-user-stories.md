# User Stories — ReleasePilot AI

**Дата:** 2026-09-20
**Формат:** INVEST, критерии приёмки в нотации Given/When/Then
**Приоритизация:** MoSCoW — `M` Must · `S` Should · `C` Could · `W` Won't (в этой версии)

---

## Персоны

**Дина — Delivery Manager.** Ведёт 1–2 релиза одновременно, каждый день отвечает
на вопрос «успеваем?». Основной пользователь, 80% времени в системе. Боль:
узнаёт о проблеме поздно и вручную собирает картину из трекера и чатов.

**Кирилл — руководитель продукта.** Заходит раз в несколько дней или читает
дайджест. Ему нужен ответ за 15 секунд: выйдем в срок или нет, и если нет —
почему. Детали не читает.

**Тимур — тимлид QA.** Смотрит только свою команду: сколько на ней висит, что
придёт на тестирование и когда. Боль: узнаёт о наплыве задач в последний день.

## E1. Доступ и аутентификация

### US-01 · Регистрация и вход `M`
**Как** пользователь, **я хочу** зарегистрироваться и войти по email или через
Google/GitHub, **чтобы** получить доступ к данным своей команды.

- Given незарегистрированный пользователь, When он входит через Google, Then создаётся профиль и он попадает на кокпит
- Given неверный пароль, When пользователь отправляет форму, Then показывается понятная ошибка без утечки информации о существовании аккаунта
- Given неавторизованный пользователь, When он открывает любой внутренний URL, Then его редиректит на страницу входа

### US-02 · Роли и видимость `S`
**Как** руководитель, **я хочу** чтобы у пользователей были роли, **чтобы**
тимлид не мог случайно изменить состав релиза.

- Given роль `viewer`, When пользователь открывает задачу, Then кнопки редактирования недоступны
- Given роль `manager`, When пользователь меняет состав релиза, Then изменение сохраняется и попадает в журнал
- Given пользователь не состоит в организации, When он запрашивает её данные напрямую через API, Then возвращается 403 (проверка на уровне RLS, не только UI)

## E2. Релизы и задачи

### US-03 · Создание релиза `M`
**Как** Delivery Manager, **я хочу** создать релиз с названием и плановой датой,
**чтобы** собирать в него задачи.

- Given форма создания, When дата в прошлом, Then валидация не пропускает
- Given созданный релиз, When он открыт, Then он в статусе `planned` и пуст

### US-04 · CRUD задач `M`
**Как** Delivery Manager, **я хочу** заводить и редактировать задачи с
приоритетом, оценкой, командой и ответственным, **чтобы** система знала состав
работ.

- Given новая задача, When не указана оценка, Then валидация требует её (оценка — основа всех расчётов)
- Given задача с оценкой 0 или отрицательной, When сохранение, Then ошибка валидации
- Given задача удаляется, When на неё есть зависимости, Then система предупреждает и предлагает сначала снять связи

### US-05 · Состав релиза `M`
**Как** Delivery Manager, **я хочу** добавлять и убирать задачи из релиза,
**чтобы** управлять объёмом.

- Given задача добавлена в релиз после его старта, When пересчёт, Then она помечается как scope drift и влияет на риск
- Given задача убрана из релиза, When пересчёт, Then метрики обновляются немедленно

### US-06 · Поиск и фильтрация `M`
**Как** Delivery Manager, **я хочу** искать задачи по названию и фильтровать по
статусу, команде, приоритету и признаку «заблокирована», **чтобы** быстро
находить проблемные места.

- Given 500 задач, When введён поисковый запрос, Then результаты появляются меньше чем за 300 мс
- Given применены фильтры, When страница перезагружена, Then фильтры сохраняются в URL

## E3. Команды и ёмкость

### US-07 · Управление командами `M`
**Как** Delivery Manager, **я хочу** заводить команды (Frontend, Backend, QA,
Analytics) и состав участников, **чтобы** считать загрузку.

### US-08 · Ёмкость на период `M`
**Как** тимлид, **я хочу** указать доступную ёмкость команды на период с учётом
отпусков, **чтобы** расчёт загрузки был честным.

- Given участник в отпуске, When задан период отсутствия, Then его часы исключаются из ёмкости команды
- Given ёмкость не задана, When расчёт, Then используется значение по умолчанию и система явно помечает это как допущение

### US-09 · Экран загрузки команд `M`
**Как** Delivery Manager, **я хочу** видеть загрузку каждой команды в процентах,
**чтобы** сразу замечать перегрузку.

- Given загрузка больше 100%, When отрисовка, Then команда выделяется красным с указанием величины перегруза
- Given несколько команд перегружены, When отрисовка, Then они отсортированы по убыванию загрузки

## E4. Зависимости и блокеры

### US-10 · Связи между задачами `M`
**Как** Delivery Manager, **я хочу** указывать, что задача блокирует другую,
**чтобы** видеть цепочки.

- Given попытка создать цикл (A блокирует B, B блокирует A), When сохранение, Then система отклоняет связь с объяснением
- Given задача блокирует три другие, When открыт её экран, Then перечислены все зависимые

### US-11 · Критическая цепочка `M`
**Как** Delivery Manager, **я хочу** видеть самую длинную цепочку зависимостей,
**чтобы** понимать, что физически не успеет.

- Given цепочка длиннее оставшегося времени, When расчёт, Then она попадает в причины риска
- Given блокер снят, When пересчёт, Then цепочка пересобирается

### US-12 · Реестр блокеров `M`
**Как** Delivery Manager, **я хочу** видеть все заблокированные задачи с
длительностью блокировки, **чтобы** разбирать их по приоритету.

- Given задача заблокирована дольше 3 дней, When отрисовка, Then она помечается как застарелый блокер

## E5. Кокпит релиза

### US-13 · Сводка текущего релиза `M`
**Как** Delivery Manager, **я хочу** на главном экране видеть всего задач,
завершено, в разработке, в тестировании, заблокировано и процент готовности,
**чтобы** за 10 секунд понять состояние.

- Given релиз с задачами, When открыт кокпит, Then показаны все шесть показателей и они сходятся с данными в БД
- Given данные загружаются, When ожидание, Then показан скелетон, а не пустой экран
- Given запрос упал, When ошибка, Then показано понятное сообщение и кнопка «повторить»

### US-14 · Уровень риска `M`
**Как** Delivery Manager, **я хочу** видеть общий уровень риска релиза
(Low/Medium/High/Critical), **чтобы** понимать серьёзность ситуации.

- Given рассчитанный риск, When отрисовка, Then показан уровень, числовой скор и список причин с их вкладом
- Given одинаковые входные данные, When расчёт выполняется повторно, Then результат идентичен (детерминированность)

### US-15 · Объяснение причин `M`
**Как** Delivery Manager, **я хочу** видеть причины риска списком, **чтобы**
знать, за что браться.

- Given риск High, When открыт кокпит, Then причины отсортированы по вкладу в скор
- Given у причины есть связанные задачи, When клик по причине, Then открывается отфильтрованный список этих задач

## E6. Прогноз даты выпуска

### US-16 · Вероятность выпуска в срок `S`
**Как** руководитель, **я хочу** видеть вероятность выпуска к плановой дате,
**чтобы** принимать решение о переносе осознанно.

- Given достаточно исторических данных, When расчёт, Then показана вероятность в процентах и метод расчёта
- Given истории мало, When расчёт, Then используется простая модель и система честно сообщает о сниженной точности

### US-17 · Прогноз на произвольную дату `S`
**Как** Delivery Manager, **я хочу** спросить про конкретную дату, **чтобы**
оценить альтернативу.

- Given вопрос «успеем ли к 30 сентября», When обработка, Then возвращается вероятность именно для этой даты

## E7. AI Delivery Assistant

### US-18 · Диалог о релизе `M`
**Как** Delivery Manager, **я хочу** спросить «что сейчас угрожает релизу?»
и получить связный ответ, **чтобы** не изучать дашборд целиком.

- Given заданный вопрос, When агент отвечает, Then все числа в ответе совпадают с рассчитанными движком
- Given агент отвечает, When генерация идёт, Then текст стримится, а не появляется через 20 секунд молчания
- Given вопрос вне компетенции системы, When обработка, Then агент честно отвечает, что не знает, вместо выдумывания

### US-19 · Поиск bottleneck `M`
**Как** Delivery Manager, **я хочу** спросить, где узкое место, **чтобы** понять,
какую команду разгружать.

- Given одна команда перегружена сильнее прочих, When запрос, Then агент называет её и показывает величину перегруза

### US-20 · Задачи под угрозой `M`
**Как** Delivery Manager, **я хочу** список задач, способных сорвать релиз,
**чтобы** заняться ими в первую очередь.

- Given список сформирован, When отрисовка, Then для каждой задачи указана причина попадания в список

### US-21 · Рекомендации `M`
**Как** Delivery Manager, **я хочу** получать конкретные рекомендации, **чтобы**
не придумывать решение самому.

- Given риск выше Low, When запрос рекомендаций, Then агент предлагает минимум одно действие с ожидаемым эффектом в цифрах
- Given рекомендация предлагает перенос задачи, When проверка, Then эта задача не блокирует остающиеся в релизе

### US-22 · Статус для руководства `S`
**Как** Delivery Manager, **я хочу** одной кнопкой получить короткий статус
релиза, **чтобы** отправить его руководителю.

- Given сгенерированный статус, When просмотр, Then он умещается в 5–7 строк и содержит готовность, риск, причины и решение
- Given статус сгенерирован, When нажата кнопка, Then его можно скопировать или отправить на email

## E8. What-if симуляция

### US-23 · Симуляция переноса задач `S`
**Как** Delivery Manager, **я хочу** посмотреть, что будет, если перенести
выбранные задачи, **чтобы** проверить гипотезу до принятия решения.

- Given выбраны задачи, When запущена симуляция, Then показаны метрики «до» и «после» рядом
- Given симуляция выполнена, When просмотр, Then данные в БД не изменились
- Given среди выбранных есть задача-блокер, When симуляция, Then система предупреждает о последствиях для зависимых

### US-24 · Подбор сценария агентом `S`
**Как** Delivery Manager, **я хочу** чтобы агент сам предложил набор задач для
переноса, **чтобы** не перебирать варианты вручную.

- Given целевой уровень риска, When агент подбирает сценарий, Then он возвращает минимальный набор задач, достигающий цели
- Given подходящего сценария не существует, When расчёт, Then агент прямо сообщает, что переносом задач проблема не решается

### US-25 · Применение сценария `C`
**Как** Delivery Manager, **я хочу** применить выбранный сценарий одной кнопкой,
**чтобы** не переносить задачи руками.

- Given сценарий применён, When проверка, Then задачи перенесены и создана запись в журнале изменений с автором и временем

## E9. Аналитика истории релизов

### US-26 · История релизов `S`
**Как** руководитель, **я хочу** видеть, сколько релизов вышло в срок и сколько
переносилось, **чтобы** оценивать качество delivery.

- Given не менее 5 завершённых релизов, When открыт экран, Then показаны доля релизов в срок и средняя задержка в днях

### US-27 · Частые причины задержек `S`
**Как** руководитель, **я хочу** видеть повторяющиеся причины срывов, **чтобы**
чинить процесс, а не симптомы.

- Given история релизов, When анализ, Then причины ранжированы по частоте
- Given одна команда чаще прочих оказывается bottleneck, When отрисовка, Then это явно указано

### US-28 · Динамика качества `C`
**Как** руководитель, **я хочу** видеть тренд по релизам, **чтобы** понимать,
улучшается ситуация или ухудшается.

## E10. Импорт из внешнего трекера

### US-29 · Импорт задач `C`
**Как** Delivery Manager, **я хочу** импортировать задачи из трекера, **чтобы**
не вводить их руками.

- Given выгрузка в поддерживаемом формате, When импорт, Then задачи, связи и версии создаются с отчётом о результате
- Given часть записей невалидна, When импорт, Then валидные загружаются, а по невалидным выдаётся построчный отчёт об ошибках
- Given импорт из корпоративного источника, When загрузка, Then применяется анонимизация имён и названий

## E11. Уведомления и дайджест

### US-30 · Email-дайджест `C`
**Как** руководитель, **я хочу** получать статус релиза на почту, **чтобы** не
заходить в систему.

- Given настроенная рассылка, When наступает время отправки, Then письмо содержит готовность, риск и главные причины

### US-31 · Оповещение о росте риска `C`
**Как** Delivery Manager, **я хочу** получать уведомление при переходе риска на
более высокий уровень, **чтобы** реагировать сразу.
