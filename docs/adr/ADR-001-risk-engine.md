# ADR-001. Движок расчёта риска: код считает, модель объясняет

**Статус:** принято
**Дата:** 2026-09-20
**Контекст:** ReleasePilot AI, Этап 2 (архитектура)

---

## Проблема

Система должна выдавать уровень риска релиза, причины и рекомендации. Возможны
три реализации:

| Вариант | Суть | Оценка |
|---|---|---|
| A | LLM получает сырые данные и сама оценивает риск | ❌ отклонён |
| B | Всё считает код, LLM только пересказывает результат | ⚠️ частично |
| C | Код считает метрики и риск, LLM интерпретирует и рекомендует | ✅ принят |

**Почему отклонён A.** Модель ошибается в арифметике на больших списках задач,
даёт разные ответы на один и тот же вопрос и не поддаётся юнит-тестированию.
Для демо на защите это критично: проверяющий задаст один и тот же вопрос дважды.

**Почему C, а не B.** Чистый расчёт даёт число, но не даёт понимания. Ценность
продукта — в объяснении и в подборе сценария, а это как раз сильная сторона
модели. Разделение ответственности: **цифры детерминированы, интерпретация
вероятностна.**

## Решение

Движок риска — набор **чистых функций** от снимка данных (`ReleaseSnapshot`),
без обращений к БД изнутри. Это обязательное условие: оно даёт бесплатную
what-if симуляцию (тот же вызов с изменённым входом) и полную тестируемость.

```
calculateRelease(snapshot, config) → ReleaseMetrics
```

LLM получает готовый `ReleaseMetrics` и отвечает за формулировки. Числа в ответе
агента обязаны совпадать с полями `ReleaseMetrics` — это проверяется тестом.

---

## 1. Входные данные

```ts
type ReleaseSnapshot = {
  release:      { id, name, plannedDate, startedAt }
  tasks:        Task[]        // id, status, priority, estimateH, spentH, teamId, addedAt, isBlocked
  dependencies: Dependency[]  // blockerTaskId → blockedTaskId
  capacity:     TeamCapacity[]// teamId, periodStart, periodEnd, availableHours
  calendar:     { workingDays: Date[] }
}
```

## 2. Базовые метрики

**Готовность считается по трудозатратам, а не по количеству задач.** Десять
мелких задач и одна крупная — разный объём работы; процент по количеству врёт.

```
readiness       = doneEffort / totalEffort
remainingEffort = Σ estimateH по незавершённым задачам
teamLoad(t)     = remainingEffort(t) / availableCapacity(t, now → plannedDate)
```

В интерфейсе показываем обе цифры — по трудозатратам (основная) и по количеству
задач (привычная), с явной подписью, какая есть какая.

## 3. Факторы риска

Каждый фактор нормирован в диапазон `0..1` и имеет вес. Сумма весов — 100.

| # | Фактор | Вес | Формула нормирования |
|---|---|---|---|
| F1 | Дефицит времени | 28 | `clamp((remainingEffort/totalCapacity − 0.85) / 0.45, 0, 1)` |
| F2 | Перегрузка команд | 24 | `clamp((max(teamLoad) − 1.0) / 0.35, 0, 1)` |
| F3 | Блокеры | 18 | взвешенная доля заблокированных задач с учётом приоритета и длительности блокировки |
| F4 | Критическая цепочка | 14 | `clamp(chainDays / remainingWorkingDays − 0.8, 0, 1)` |
| F5 | QA-воронка | 10 | доля задач, которые не успеют пройти тестирование до даты релиза |
| F6 | Дрейф скоупа | 6 | доля трудозатрат, добавленных в релиз после его старта |

```
riskScore = Σ (Fi × weightᵢ)   →   0..100
```

**Калибровка F2** выполнена по реальному опыту Delivery Manager: загрузка 135%
даёт фактору значение 1.0 (максимум), 110% — около 0.29.

## 4. Уровень риска: скор плюс правила эскалации

Одного скора недостаточно. Delivery Manager мыслит не баллами, а правилами:
«две критические задачи заблокированы — значит, горит», независимо от того, как
выглядит средневзвешенная сумма.

**Базовые пороги по скору:**

| Скор | Уровень |
|---|---|
| 0–24 | Low |
| 25–49 | Medium |
| 50–74 | High |
| 75–100 | Critical |

**Правила эскалации (поднимают уровень, никогда не понижают):**

| Условие | Минимальный уровень |
|---|---|
| Загрузка любой команды ≥ 105% | Medium |
| Загрузка любой команды ≥ 130% | High |
| Хотя бы одна заблокированная задача приоритета P0 | High |
| Две и более заблокированных задачи приоритета P1 | High |
| Критическая цепочка длиннее оставшегося времени | High |
| Вероятность выпуска в срок < 40% | High |
| Вероятность выпуска в срок < 20% | Critical |

**Проверка на примере из постановки задачи.** QA загружен на 135%, две
критические задачи заблокированы, backend-задача блокирует три frontend-задачи,
часть задач не успевает тестирование → правила эскалации дают **High**. Совпадает
с экспертной оценкой. Загрузка 110% в отсутствие других проблем даёт Medium
со скором в верхней части диапазона — тоже совпадает («Medium, почти High»).

Скор при этом сохраняется и показывается: он нужен для **динамики** — упал риск
за сутки или вырос, — тогда как уровень нужен для **решения**.

## 5. Причины риска

Каждый сработавший фактор и каждое сработавшее правило порождают запись:

```ts
type RiskReason = {
  code:         string    // 'TEAM_OVERLOAD' | 'CRITICAL_BLOCKER' | ...
  severity:     'low' | 'medium' | 'high'
  contribution: number    // вклад в скор, для сортировки
  facts:        Record<string, number|string>  // { team: 'QA', load: 1.35 }
  taskIds:      string[]  // связанные задачи — для перехода по клику
}
```

Текст причины **не хранится в движке**. Движок отдаёт код и факты, текст
формирует слой представления или LLM. Это разделяет вычисление и формулировку
и позволяет менять тон объяснений, не трогая расчёт.

## 6. Прогноз даты (Монте-Карло)

Оценка трудозатрат — это не факт, а предположение. Поэтому прогноз даётся
вероятностью, а не бинарным «успеем / не успеем».

- Для каждой незавершённой задачи берётся распределение Beta-PERT:
  `оптимистично = estimate × 0.8`, `вероятно = estimate`,
  `пессимистично = estimate × k`, где `k` — коэффициент занижения оценок,
  вычисленный по истории завершённых релизов (по умолчанию 2.0).
- 5 000 итераций. В каждой — задачи расставляются по времени с учётом
  зависимостей и ёмкости команд, вычисляется дата завершения.
- `P(в срок)` = доля итераций, завершившихся не позже плановой даты.
- **Фолбэк:** если завершённых релизов меньше пяти, используется детерминированный
  расчёт `remainingEffort / capacity`, и система **явно сообщает** о сниженной
  точности (US-16).

Для генератора случайных чисел используется фиксируемое зерно: одинаковый вход
даёт одинаковый результат, иначе тесты нестабильны, а демо невоспроизводимо.

## 7. What-if симуляция

Прямое следствие того, что движок — чистая функция:

```ts
simulate(snapshot, { excludeTaskIds, moveToReleaseId, extraCapacity })
  → { before: ReleaseMetrics, after: ReleaseMetrics, delta }
```

**Подбор сценария агентом** (US-24) — жадный алгоритм:

1. Кандидаты — незавершённые задачи, отсортированные по: низкий приоритет →
   высокий вклад в перегрузку узкого места → отсутствие зависимых задач.
2. **Жёсткий фильтр: задача-кандидат не должна блокировать задачи, остающиеся
   в релизе.** Без этой проверки рекомендация становится вредной.
3. Добавляем по одной, пересчитываем, останавливаемся при достижении целевого
   уровня риска.
4. Если цель недостижима — агент обязан сказать об этом прямо, а не предлагать
   бессмысленный набор.

## 8. Конфигурация

Все доменные величины вынесены в один файл `config/risk.ts` — меняются без
правки логики:

```ts
export const RISK_CONFIG = {
  weights:              { F1: 28, F2: 24, F3: 18, F4: 14, F5: 10, F6: 6 },
  levelThresholds:      { medium: 25, high: 50, critical: 75 },
  escalation: {
    teamLoadMedium:     1.05,
    teamLoadHigh:       1.30,
    probabilityHigh:    0.40,
    probabilityCritical:0.20,
  },
  staleBlockerDays:     3,
  defaultFocusFactor:   0.65,   // 40 ч номинала → 26 ч полезной ёмкости
  estimatePessimism:    2.0,
  monteCarloIterations: 5000,
}
```

**Статус значений по умолчанию:** предварительные, согласованы с Delivery
Manager по порядку величин. Подлежат калибровке на реальных данных на этапе
разработки коннектора к трекеру.

## 9. Последствия решения

**Плюсы:**
- метрики детерминированы и покрываются юнит-тестами;
- what-if достаётся бесплатно, без второй реализации расчёта;
- объяснения можно менять, не трогая вычисления;
- LLM не может соврать в цифрах — они приходят к ней уже посчитанными.

**Минусы и чем компенсируем:**
- веса и пороги подобраны экспертно, а не обучены на данных → вынесены
  в конфиг и снабжены планом калибровки;
- чистые функции требуют собирать полный снимок данных перед расчётом →
  на больших объёмах понадобится кэширование снимка.

## 10. Требования к тестам

- каждый фактор — отдельный юнит-тест на граничных значениях;
- тест детерминированности: один вход → один и тот же выход;
- тест на сценарий из постановки задачи: QA 135% + два блокера → **High**;
- тест безопасности рекомендаций: предложенная к переносу задача никогда не
  блокирует остающиеся в релизе;
- тест согласованности: числа в ответе агента равны полям `ReleaseMetrics`.
